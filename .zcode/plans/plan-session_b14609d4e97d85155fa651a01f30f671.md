# 生成 2026-11-02(美股)晨报报告 — 执行计划

## Context
用户要求生成 11 月 3 日(北京时间)发布的报告,报告日 T = 2026-11-02(周一美股交易日)。这是 v8.2(Admin 订阅无白名单 + L/E 分级 + LLM triage 选材)改造后的**首次生产运行**,10-30 期仅做过 /tmp 快照级验证。执行序列沿用 cron_daily.sh 的标准流程,但分步手动执行以便在 Stage 0 与章节生成之间插入 triage 质量检查点。

## 执行步骤

1. **前置检查(只读,~1 分钟)**
   - 查 subscription_content:T=11-02 的 The Close / Closing Bell 转录是否已入库(README:次日上午 10 点后稳定,现在 18:00+,应已就绪);缺失则该节目按缺源降级(errors 记录),不阻塞。
   - 确认 `/tmp/morning_brief_cron.lock` 无残留锁。

2. **Stage 0:冻结快照 + triage(~10-12 分钟)**
   ```bash
   cd /opt/guanhetech/tools/morning-brief
   # 导出 cron_daily.sh 同款 zcode provider 环境变量(HOME/ZCODE_DATA_BASE_DIR/
   # ZCODE_PERSONAL_PROVIDER_CONFIG_FILE/ZCODE_BUILTIN_PROVIDER_CONFIG_FILE/PATH)
   /root/miniconda3/envs/guanhe/bin/python build_snapshot.py --date 2026-11-02
   ```
   - 默认跑 triage(轻扫→分块 LLM 分拣→triage.json→组池),产物写入 `backend/reports/morning-brief/2026-11-02/`
   - 预计:~1,900 候选、4-5 块并行、~0.3-0.4M 输入 / ~0.1-0.15M 输出 tokens

3. **triage 质量检查点(花章节 tokens 前的人工闸门)**
   - 检查 triage.json + snapshot.news_macro:三层非空、主题合理(无央行污染、选举类已合并)、digest 周一晨报应非空
   - 不合格 → 调 `_TRIAGE_PROMPT` 后 `--force-triage` 重跑(仅重花 triage tokens),再进入下一步

4. **章节生成 + 核验 + 发布(~25-40 分钟)**
   ```bash
   /root/miniconda3/envs/guanhe/bin/python run_pipeline.py 2026-11-02 --style cn
   ```
   - 两段编排(7 组并行 + outlook 二段)→ 确定性核验 + LLM 轻核验 → 修订循环 → assemble/publish
   - 预计 ~9-14M 输入(≈93% 缓存)/ ~0.3-0.5M 输出

5. **交付汇报**
   - 退出码与发布路径(final/report.md);各节用时与 tokens 汇总(从 state.json + zcode DB);口径头与已知降级项(errors/notes)
   - 若退出码 2(NEEDS_HUMAN_REVIEW):**停在那里汇报问题清单等人工仲裁**,不自动强推发布(10-30 期的先例)

# 李晔需求
1. 数据库A存放我自己没读过的信息源（with tags)。信息源可以标注高中低三个重要性。
2. 数据库B存放我已经读过的信息源（with tags)。信息源可以标注高中低三个重要性。
3. 数据库C存放我的想法（with tags)。这些想法往往是tag的来源，比如开始关注一个新的主题了，就建立了相关的新tag。想法可以标注高中低三个重要性。
4. 数据库A, B, C里的每一条信息都可以选择与公司同事分享/不分享。关于被分享的信息，同事们可以看到高中低三个重要性。
5. 数据库A, B, C里的每一条信息中如果设计具体的投资标的，系统可以进行识别，并将该条信息相关的tag自动贴到这些投资标的上。
6. 除了数据库，我们还可以建立一个市场跟踪系统。提到市场跟踪系统，大家往往想到的是stock mkt indices, macro data, etc. 这些我们自然可以放在系统里。但我认为更重要的一个系统是这样的：当我选定一个tag时，系统可以告诉我相关的标的都有哪些，系统可以construct equal-weight and value-weight portfolios of these assets；这样我就可以看到这个tag对应的标的目前的走势，尤其是对一些新闻事件的反应。
7. 更高级一个功能是，对于每个tag，系统可以在网上调取相关的新闻事件（包括earnings announcements/transcripts, etc.）。这个或许可以通过以下两种手段实现。第一，在我们的数据库中，每个tag对应了一堆文档，如果一个新闻事件的textual distance和这些文档接近，那就贴上这个tag。第二个手段是，每个tag对应了一堆标的，涉及相关标的的新闻事件自然也被贴上这个tag。第二个手段更有操作性。

以上这个系统的核心其实就是主题投资。关于长期的系统建构，我有以下想法（不是最近两三个月的工作）。对于每个主题，我们也可看momentum, value, profitability, idiosyncratic vol.等等这些factor，也包括一些技术分析指标（针对tag-level equal-weight and value-weight portfolios）。主题层面的factor/characteristic/technical indicators可能比个股层面更有预测能力。另外，主题层面我们也可以定义对于宏观数据的beta。所以，以上系统区别于传统的投研系统在于一切基于tag（主题）而非个股。经典的分析个股的框架，factor/technical/macro cycle ...，都可以应用到主题层面。为什么按照主题而非个股去建立一个框架呢？因为市场动态是主题/叙述来驱动的，这是个根本规律。

我还想到一个功能：对未来重要事件的记录。比如2027年美国的debt ceiling谈判可能开始，这个事情我们最好提前两三个月开始布局（比市场关注的要早一些）。这是一个对未来可能发生事情的判断。我们需要建立一个共同的calendar吗？但是像这种，很难定到具体哪一天，不知道能不能定一个range。这个calendar我们一打开，选择未来三个月、六个月、一年，就能看到相关的主题或催化事件。

目前我们的系统是为了记录 “已经发生了什么” 而设计的，我们应该还有一个记录 “未来可能发生什么” 的系统，不一定分要分开设计，都只是功能而已。对未来的判断 + 未来可能发生的事件，这些东西不像pre-scheduled news announcenments，是没有具体时间的，只能定一个range，但是这个range可以展示出来。当然，这些对未来的判断 + 未来的事件，也可以加tag（和之前数据库里的tag是一回事，tag=主题）。

## 一、按处理流程的问题记录

### 阶段 0 · 前置检查

**P1 [代码缺陷·已修] Closing Bell 日期匹配零填充 bug**
- **现象**(11-02 期):`prep_workspace` 报 `no Closing Bell podcast rows with 11/02/26 title date`,CB 转录判缺失;但 DB 里主段/Overtime 明明存在(标题 `Closing Bell: 11/2/26`)。
- **根因**:`_cb_title_has_date` 用 `strftime("%m/%d/%y")` 生成 `"11/02/26"` 做子串匹配,而 CNBC 标题个位日不补零(`"11/2/26"`)。10-30 期因日号 30 是两位数而未暴露——**潜伏 bug,逢每月 1-9 日必触发**。
- **处置**:改正则为 `0?{月}/0?{日}/(两位年|四位年)`(补零/不补零双兼容);7 个单测用例全过;端到端取回主段 55,080 + Overtime 53,696 字符。
- **教训**:前置检查时我还误读了 `fetch_closing_bell` 的返回结构(键存在但值为 None 判成"存在"),先入为主地跳过了深查——**返回结构语义要按代码定义读,不能按直觉读**。

**P2 [外部故障·ingest 侧] The Close 晚间整期连续迟到**
- **现象**:11-02、11-03 两期的 The Close 整期转录分别迟到约 36/14 小时入库(频道内其他短视频正常)。11-02 期报告因此以无转录降级版发布(次日转录才到)。
- **处置**:管线侧按缺源降级(`errors` 记录,01-03 节素材变薄);**根治需家用 Worker 抓取侧排查(建议检查 youtube 频道晚间长视频的抓取批次)**。
- **附带发现**:11-02 期的 The Close 现已入库("Michigan Midterms, Apple Earnings & the Tech Selloff",72k);是否花 ~7M tokens 重生成 11-02 报告,待用户决定。

### 阶段 1 · Stage 0 快照 + triage

**P3 [环境故障·已定位] Python 3.13 vfork 死锁 —— 本次测试最重的根因**
- **现象**(11-03 期,三次复现):triage 的并行分块(线程池 + `subprocess.run` 拉 zcode)整体静默卡死——主线程与工作线程全部 futex 空等、**无任何 zcode 子进程**、DB 无活动查询、py-spy 无法附着;出现过的一个子进程**继承父进程的 exe/cmdline(仍是 python)**,卡在 exec 前的 futex/do_poll。单块调用(探测)却正常。11-02 期同路径 4-5 路并行曾完全正常。
- **根因**:Python 3.13 的 subprocess 默认用 `vfork`;vfork 子进程在 exec 前与父进程共享地址空间,多线程/特定堆状态下**偶发卡死在 exec 前**(与全部症状吻合:子进程显示父进程 cmdline、时好时坏、fork 后无 exec)。
- **处置**:
  1. 根因修复:`build_snapshot.py` 与 `run_pipeline.py` 导入时 `subprocess._USE_VFORK = False`(代价每次调用 ~1ms),实测 python→zcode 调用 7.2s 正常返回;**11-03 期章节生成的全部 agent 子进程均正常 exec,零复发**。
  2. 当时的绕道(根因修复前):triage 改 **bash 编排**——python 只做无 fork 的准备(候选分块写文件)/汇总,`zcode -p` 由 bash 循环拉起,5 块产出与原生路径完全一致。
- **教训**:静默卡死类故障必须先拿到进程级证据(wchan/exe/cmdline)再动手;`| tail` 管道会吞掉全部中间日志,排障命令必须全量落盘。

**P4 [代码缺陷·已修] triage 分块无重试**
- **现象**(11-02 期首跑):后台构建中 triage 整体失败,news_macro 静默回退正则路径(zcode `Turn execution failed`,provider 间歇错误)。
- **处置**:`_triage_chunk` 加分块级重试(20s 退避 ×1 次);另加 `TRIAGE_WORKERS=1` 串行降级开关(绕线程池,配合 vfork 问题时期使用)。
- **说明**:provider 间歇错误两天共放倒 5 次 agent/triage 调用,重试与幂等续跑全部兜住——**这是外部抖动,重试是正解**。

**P5 [操作缺陷·已改] 命令管道吞日志与退出码**
- **现象**:两次关键排障信息丢失——`... | tail -30` 让 Stage 0 开头的 `[triage] FAILED` 不可见;`| tail -60` 让 run_pipeline 的真实退出码被 tail 的 0 掩盖(实际 rc=2)。
- **处置**:排障/生产命令改为全量重定向落盘(`> file 2>&1`)或 `tee`;后台任务判定以 state.json 为准,不信管道退出码。

**P6 [代码缺陷·已修] fetch_the_close 窗口逻辑 bug**
- **现象**(11-03 期):转录已在库,`fetch_the_close` 仍返回缺失。用户从 reports 模块发现"11-04 的 the close report"存在,倒逼复查。
- **根因**:窗口循环 `for (21,23),(20.5,24)` 的写法是"主窗口**命中任意行**就 break,再对这批行做自识别,失败即放弃"——当晚 21:10 先命中中期选举特辑(56k ≥ 50k 门槛),自识别失败后**加宽窗口从未被执行**,而真正的 The Close 在 23:00:27 UTC(93.6k)。
- **处置**:改为**逐窗口内自识别**,全部不中才放宽下一档,并加第三档 `(20.5, 25.0)`;回归验证 11-02/11-30…均正常,11-03 取回 "Midterms, Affordability & Markets" 93,619 字符。
- **教训**:"找到候选"与"找到目标"是两个谓词,循环退出条件绑错了前者。

**P7 [流程风险·已规避] 残缺 triage.json 被复用**
- **现象**:`--triage-limit 30` 探测会写 30 条的 triage.json 到正式工作区;此后重建快照会"复用"这份残片(复用逻辑不校验候选量)。
- **处置**:意识到后立即全量重跑覆盖;**改进建议(未做)**:`load_triage` 校验 `candidates` 与当窗实际候选量一致才复用,或探测模式写独立路径。
